# 8around SNS

## 프로젝트 개요 및 배포 URL

생각을 짧게 나누는 SNS입니다. 설계, 구현, 리뷰, 배포까지 Claude Code와 함께 진행했습니다.

- **배포:** [https://8around-new-sns-beta.vercel.app](https://8around-new-sns-beta.vercel.app)

### 기능

| 구분 | 기능 |
|---|---|
| 요구 기능 | 회원가입, 로그인과 로그아웃, 팔로우와 팔로잉, 게시글 작성, 댓글, 대댓글 |
| 추가 기능 | 팔로잉한 사람의 글만 모은 피드, 좋아요와 좋아요한 글 모음, 내 글과 댓글 수정 및 삭제, 프로필 편집(별명, 소개, 관심사, 사진), 다크 모드, 모바일과 태블릿 화면 |

대댓글 깊이는 과제 명세에 없어 한 단계로 정했습니다. 댓글에는 답글을 달 수 있고, 답글에 다시 답글을 달 수는 없습니다. 끝없이 중첩되면 모바일 화면에서 읽기 어렵고 조회가 재귀가 되기 때문이며, DB 정책이 이 깊이를 막습니다.

### 체험 방법

가입하면 바로 로그인됩니다. 메일 인증은 없습니다.

1. **회원가입:** 이메일과 비밀번호, 별명을 넣어 가입합니다.
2. **글 작성:** "새 글 쓰기"(모바일은 아래 탭의 "새 글")로 글을 올리면 "전체" 피드 맨 위에 보입니다.
3. **댓글과 답글:** 글을 눌러 댓글을 달고, 댓글의 "답글 달기"로 답글을 답니다.
4. **팔로우:** 피드에서 다른 사람의 이름을 눌러 프로필로 가서 "팔로우"를 누릅니다.
5. **팔로잉 피드:** 왼쪽 메뉴(모바일은 아래 탭)의 "팔로잉"에서 팔로우한 사람의 글만 봅니다.

## 로컬 실행 방법

동작 확인은 위의 배포 URL에서 해 주세요. 직접 실행하려면 아래 셋 중 하나를 고릅니다.

**공통 준비**

- Node 20.11 이상 (CI는 Node 22로 돌립니다)
- `npm install`

### 1. 검사만 돌리기 (계정, Docker 모두 필요 없음)

린트, 타입 검사, 단위 테스트, 규칙 검사를 한 번에 돌립니다.

```bash
npm run verify
```

### 2. 로컬 Supabase로 실행하기 (Docker 필요, 계정 필요 없음)

CI의 E2E가 쓰는 방식과 같습니다. `supabase start`가 컨테이너를 띄우면서 `supabase/migrations/`를 모두 적용하고, 메일 인증은 `supabase/config.toml`에서 이미 꺼져 있습니다.

```bash
npx supabase start
npx supabase status -o env   # API_URL, ANON_KEY 값을 확인
cp .env.example .env.local   # 위 두 값을 각각 URL, ANON_KEY 칸에 넣기
npm run dev                  # http://localhost:3000
```

### 3. 내 Supabase 프로젝트로 실행하기 (Supabase 계정 필요)

```bash
cp .env.example .env.local   # 프로젝트 URL과 anon 키 넣기
npx supabase login           # 처음 한 번. 이미 로그인돼 있으면 건너뜀
npm run db:link              # 원격 프로젝트에 연결
npm run db:push              # 마이그레이션 적용
npm run dev
```

- Supabase 대시보드의 Authentication 설정에서 **Confirm email**을 꺼야 가입 직후 로그인됩니다.
- 이 방식으로 `npm run test:e2e`를 돌리면 그 DB에 테스트 계정 두 개가 남습니다.

## 하네스 구성 설명

### 풀려고 한 문제

AI 에이전트와 며칠 동안 작업하면 세 가지 문제가 반복됩니다.

1. **세션이 바뀌면 맥락이 사라집니다.** 어제 합의한 규칙을 오늘은 모릅니다.
2. **코드만 보고 "될 겁니다"라고 보고합니다.** 실제로 화면을 열어보지 않습니다.
3. **갈림길에서 혼자 정하고 진행합니다.** 나중에 보면 왜 그렇게 했는지 남아 있지 않습니다.

그래서 규칙은 문서로 남기고, 그중 AI가 확인할 수 있는 것은 스크립트로 옮겼습니다. 사람의 기억이 아니라 저장소가 품질을 지키도록 하는 것이 목표였습니다.

### AGENTS.md 작성 항목

[AGENTS.md](AGENTS.md)에 적은 17개 항목입니다. (에이전트)가 붙은 항목은 AI가 작업할 때 지키는 항목이고, 나머지는 사람과 AI가 함께 지킵니다.


| 항목                                      | 왜 넣었나                                               | 무엇을 지키나                                      |
| --------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| 1. 함수는 찾고, 따지고, 분리한다                    | AI는 이미 있는 함수를 찾지 않고 파일 안에 새로 쓰기 쉽습니다                | 순수 함수는 `lib/utils/`에 모이고 테스트가 붙습니다           |
| 2. 같은 것을 두 번 만들지 않는다                    | 비슷한 컴포넌트가 두 벌 생기면 한쪽만 고쳐져 화면이 어긋납니다                 | 컴포넌트와 로직이 한 곳에만 있습니다                         |
| 3. 사실은 한 곳에만 적는다                        | 같은 내용이 두 곳에 있으면 결국 하나가 낡습니다                         | 스키마, 타입, 디자인 토큰, 개발 지침, 일정마다 출처가 하나입니다       |
| 4. 근거 없이 코드를 쓰지 않는다                     | "보통 이렇게 합니다"로 쓴 코드는 이 프로젝트에 맞는지 알 수 없습니다            | 모든 판단의 근거가 `파일:줄`이나 실행 결과로 남습니다              |
| 5. 사실만 보고한다 (에이전트)                      | AI는 실행하지 않고도 "될 겁니다"라고 보고합니다                        | 테스트 결과와 동작 여부가 실제 출력으로 보고됩니다                 |
| 6. 지시받기 전까지 임의로 진행하지 않는다 (에이전트)         | AI가 갈림길에서 혼자 정하면 방향이 제 의도와 달라집니다                    | 방향은 사람이 정하고, AI는 선택지와 추천을 제시합니다              |
| 7. 사용자 환경을 건드리는 명령은 먼저 묻는다 (에이전트)       | 권한을 좁히는 DB 변경을 묻지 않고 적용했다가 배포된 서비스의 좋아요 수가 틀어졌습니다   | 개발 서버, 원격 DB, 푸시, 패키지 설치가 사람의 승인 없이 바뀌지 않습니다 |
| 8. 스키마가 타입의 출처다                         | 손으로 쓴 타입과 실제 컬럼이 어긋나면 런타임에서만 터집니다                   | DB 타입은 마이그레이션에서 생성되어 항상 스키마와 같습니다            |
| 9. 검증은 신뢰 경계에서, 권한은 RLS에서               | 브라우저 검증은 요청을 직접 보내면 뚫리고, 액션마다 권한을 확인하면 빠지는 경로가 생깁니다 | 입력은 서버가 검증하고, 소유권은 DB가 모든 경로에서 막습니다          |
| 10. 화면은 상태 네 가지가 없으면 미완성이다              | 성공 경로만 만들면 로딩, 빈 목록, 없는 주소, 에러에서 화면이 깨집니다           | 모든 화면에 로딩, 빈 상태, 없음, 에러 처리가 있습니다             |
| 11. 한 번에 한 기능                           | 화면을 다 만들고 데이터를 나중에 붙이면 마지막에 통합 문제가 몰립니다             | PR 하나가 기능 하나라서 리뷰와 되돌리기가 쉽습니다                |
| 12. `.env`, `.env.local`을 열지 않는다 (에이전트) | AI가 읽은 값은 대화, 로그, 커밋 어디에든 옮겨질 수 있습니다                | 시크릿 값이 대화 기록과 저장소에 남지 않습니다                   |
| 13. 규칙이나 구조가 바뀌면 문서를 고친다                | 낡은 문서를 읽은 다음 세션의 AI는 틀린 내용을 따릅니다                    | 문서가 항상 현재 코드와 맞습니다                           |
| 14. 갈림길은 기록한다                           | 코드에는 고른 것만 남아, 버린 선택지와 이유가 사라집니다                    | 같은 논의를 반복하지 않고, 결정을 뒤집을 때 이유를 추적할 수 있습니다     |
| 15. 주석은 TSDoc으로 쓰고 사실만 적는다              | 주석이 길고 판단까지 담으면 코드와 어긋났을 때 무엇을 믿을지 모릅니다             | 주석은 동작과 제약만 담고, 판단의 이유는 결정 기록에 있습니다          |
| 16. 화면은 열어서 확인한다 (에이전트)                 | 코드만 읽고는 실제 화면에서 깨지는 것을 알 수 없습니다                     | Playwright로 누르고 본 결과(스크린샷, 콘솔)가 완료의 근거가 됩니다  |
| 17. 사용자 흐름을 바꾸면 E2E를 같이 고친다             | 단위 테스트는 가짜 DB로 돌아 화면 흐름이 끊긴 것을 잡지 못합니다              | 가입부터 팔로우까지의 흐름이 PR마다 CI에서 끝까지 도는지 확인됩니다      |


이 중 AI가 확인할 수 있는 것은 `npm run verify`가 커밋 전에 검사하고, 심사 시나리오는 CI의 E2E가 돌리고, 나머지는 PR의 AI 리뷰와 `/pr`, `/pr-review` 스킬이 봅니다.

### 사람이 바뀌어도 품질이 같은 이유

새로 온 사람이나 다른 AI 도구가 기능을 더해도 결과가 같게 나오도록, 품질을 사람의 기억이 아니라 세 겹의 장치에 맡겼습니다.

#### 1. 무엇을 지킬지는 문서 하나에 있습니다

- 규칙은 `AGENTS.md` 한 곳에만 있고 `CLAUDE.md`는 그 파일을 가리키기만 합니다. AI 도구와 사람이 같은 문서를 읽습니다.
- "왜 이렇게 했나"는 결정 기록 51개에 버린 선택지와 함께 남아 있습니다. 새로 온 사람이 같은 논의를 반복하거나 이미 버린 방식을 다시 고르지 않습니다.
- 결정을 빠뜨리면 리뷰가 잡습니다. 파비콘 PR에서 색을 토큰 밖에 적은 이유가 PR 본문에만 있다는 지적을 받아 결정 기록을 더했습니다 (PR #111).

#### 2. 기계가 볼 수 있는 것은 기계가 봅니다

- `npm run verify` 한 줄이 린트, 타입 검사, 테스트, 규칙 검사를 돌리고, CI가 PR마다 같은 명령에 빌드와 E2E를 더해 돌립니다.
- 규칙 검사는 로딩, 없음, 에러 화면이 빠진 라우트, 깨진 문서 링크, 목차에 없는 결정 기록을 잡습니다. 규칙을 외우지 않아도 빠뜨리면 실패합니다.
- E2E는 가입부터 팔로우까지 요구 기능 흐름을 끝까지 지납니다. 대댓글 진입점이 사라졌던 코드로 돌리면 답글 단계에서 실패하는 것을 확인했습니다 (PR #104).

#### 3. 판단이 필요한 것은 리뷰가 보고, 리뷰도 검증합니다

- PR을 열면 AI가 `AGENTS.md` 기준으로 리뷰합니다. 머지된 PR 108개 중 42개에서 지적 51건을 남겼고 35건이 반영됐습니다.
  - 로그인 리다이렉트 응답에 캐시 방지 헤더가 빠져 세션 쿠키가 캐시될 수 있던 경로 (PR #6)
  - 답글 화면을 거치면 뒤로 가기가 엉뚱한 곳으로 가던 문제 (PR #98)
  - 에디터가 옛 버전으로 덮어써 계획 문서가 되돌아간 것 (PR #11)
- 리뷰를 그대로 따르지 않습니다. `/pr-review` 절차가 지적마다 레포에서 먼저 확인하게 해서 8건은 근거와 함께 반박했습니다. 실제 DB에 중복이 0건인 것을 확인하고 마이그레이션 지적을 반박한 경우가 그렇습니다 (PR #71).

#### 한계

- 하네스가 막지 못한 일도 있었습니다. 권한을 좁히는 마이그레이션을 먼저 적용해 배포본의 좋아요 수가 틀어졌고, 이후 DB 적용은 건마다 묻고 좁히는 변경은 "넓히기, 코드 배포, 좁히기" 세 단계로 나누게 규칙을 바꿨습니다.
- 지금은 혼자 Private 저장소에서 작업해서 `main` 브랜치 보호를 켜지 않았습니다. CI 통과를 머지 조건으로 강제하지 않고 규칙과 `/pr` 절차로 지킵니다.
  협업을 시작하면 브랜치 보호로 CI(verify, e2e) 통과와 리뷰를 머지 조건으로 걸어, 사람이 절차를 건너뛰어도 품질이 떨어지지 않게 하겠습니다.

## 구현 중 내린 주요 기술적 의사결정과 트레이드오프

### 1. 권한 검사는 서버 코드가 아니라 DB 정책(RLS)에 둔다

- **상황**
  - 게시글 수정과 삭제, 댓글 수정과 삭제, 팔로우 취소는 모두 "이것이 내 것인가"를 확인해야 합니다.
  - 이 확인을 서버 코드의 기능마다 따로 넣으면, 기능이 늘어날 때 하나라도 빠뜨리는 순간 남의 글을 고치거나 지울 수 있게 됩니다.
  - 게다가 Supabase는 브라우저에 공개된 anon 키로 DB에 직접 요청할 수 있습니다. 서버 코드를 거치지 않는 요청에는 서버 코드의 확인이 아예 걸리지 않습니다.

- **해결방법**
  - Postgres RLS 정책 한 곳에 쓰고, 서버 코드에는 같은 검사를 두지 않았습니다.

- **트레이드오프**
  - 서버 코드만 봐서는 권한이 보이지 않아 `supabase/migrations/`를 함께 읽어야 합니다.

### 2. 좋아요 목록이 남에게 보이던 문제

- **상황**
  - "좋아요한 글" 화면을 만들면서 `post_likes` 테이블을 내 id로 거르는 조회를 추가했습니다.
  - 그런데 이 테이블의 조회 정책이 "누구나 본다"(`using (true)`)라서, 다른 사람의 id를 넣으면 **그 사람이 좋아요한 글 목록**이 그대로 나왔습니다.
  - 화면은 내 id로만 조회하므로 웹 서비스를 쓰는 동안에는 드러나지 않습니다.
  - 브라우저에 공개된 anon 키로 Supabase에 요청을 직접 보내면 누구나 볼 수 있었습니다.
  - "좋아요한 글"은 개인 모음이라 막기로 했습니다.

- **막으면 생기는 문제**
  - 조회 정책을 "본인 좋아요만 본다"로 좁히면, 좋아요 수를 세던 `post_likes(count)` 조회도 정책을 따르게 됩니다.
  - 모든 글의 좋아요 수가 보는 사람 자신의 좋아요(0 또는 1)로 바뀝니다.
  - 누가 눌렀는지는 숨기고, 수는 계속 모두에게 보여줄 방법이 필요했습니다.

- **해결책**
  - **(A) 좋아요 수를 세어 숫자만 돌려주는 DB 함수 `like_count`**
    - 좋아요 기록은 이제 본인 것만 읽히지만, 이 함수는 DB 안에서 모든 사람의 좋아요를 셀 수 있게 만들었습니다(`security definer`).
    - 대신 밖으로 내보내는 값은 "이 글의 좋아요 3개" 같은 숫자 하나뿐이라, 누가 눌렀는지는 알 수 없습니다.
    - 서버 코드는 글을 읽을 때 `post_likes(count)` 대신 `like_count`를 달라고 요청 항목 이름만 바꾸면 됩니다.
  - **(B) `posts` 테이블에 `like_count` 컬럼과 트리거**
    - 좋아요가 추가되거나 지워질 때 트리거로 값을 올리고 내립니다.
    - 읽기가 가장 쌉니다.

- **해결방법:** **(A)** 로 결정
  - (B)는 이미 쌓인 좋아요 수를 컬럼에 채우고, 두 사람이 동시에 누를 때 값이 꼬이지 않게 하고, 컬럼 값과 실제 좋아요 수가 어긋났을 때 되돌리는 방법까지 만들어야 합니다.
  - 스키마 변경이 함수 하나인 (A)로 충분했습니다.

- **트레이드오프**
  - 글을 읽을 때마다 그 글의 좋아요를 새로 셉니다. 기본키 `(post_id, user_id)`의 앞부분이 이 조회를 받지만, 한 글의 좋아요가 아주 많아지면 목록을 읽는 비용이 같이 커집니다. 그때는 (B)로 옮겨야 합니다.
  - 정책을 건너뛰는 함수가 하나 늘었습니다. 함수 본문을 고치면 수 말고 다른 값이 새지 않는지 다시 확인해야 합니다.

### 3. 불필요한 인증 서버 요청

- **상황**
  - 배포 환경이 느려 원인을 따라가 보니, 응답 시간이 Server와 Supabase 사이 왕복 횟수에 비례했습니다.
  - 한 요청 안에서 세션 확인을 두 번 하고 있었습니다.

- **해결방법**
  - 두 번째 세션 확인은 네트워크 없이 JWT 서명만 검증하도록 바꿨습니다.
  - 팔로잉 피드는 서버가 세 번 나눠 읽던 것을 DB 함수 하나로 합쳤습니다.

- **제외된 방법**
  - 첫 확인 결과를 헤더로 넘기는 방법. 검증은 한 곳으로 모이지만 헤더는 위조할 수 있습니다.

- **트레이드오프**
  - Supabase 프로젝트가 비대칭 키를 써야 이득이 있어서, 키 방식을 먼저 확인했습니다.

### 4. 버튼 중복 호출

- **상황**
  - 브라우저에서 직접 요청 수를 셌습니다.
  - 보통 더블클릭은 괜찮았지만, 아주 짧은 간격의 클릭 두 번은 글쓰기, 댓글, 팔로우, 로그인 모두 요청이 두 번 갔습니다.

- **해결책**
  - (A) 화면이 다시 그려지기 전에 즉시 막는 클라이언트 잠금
  - (B) 서버에서 중복 키로 거르기

- **해결방법:** **(A)** 로 결정
  - (B)는 테이블마다 제약과 키 수명 정책이 필요해 이 규모에는 과했습니다.

- **트레이드오프**
  - 중복 방지 잠금은 브라우저 탭 안에만 있습니다.
  - 개발자 도구나 스크립트로 요청을 직접 두 번 보내거나, 두 탭에서 동시에 제출하면 서버는 둘 다 저장합니다.
  - 서버에서 막으려면 요청마다 고유 키와 DB 제약이 필요합니다. 같은 글을 두 번 쓰는 것과 결과가 같아 데이터가 깨지지는 않으므로 이 비용을 들이지 않았습니다.

## 시간이 더 있었다면 개선했을 부분

### 1. 기획에 더 시간을 쓰겠습니다.

- **아쉬운 점**
  - 요구 기능을 빠르게 구현하려고 기획을 가볍게 잡고 시작했더니, 작업 중에 기획이 계속 바뀌었습니다.
  - 기술적인 선택, 디자인, 페이지별 변경사항을 구현하다가 다시 기획하는 일이 반복되면서 작업 속도가 느려졌습니다.

- **실제로 바뀐 것:** 착수 전에 정하지 않은 네 가지가 작업 중에 다시 결정됐습니다.
  - **디자인 기준**
    - 당근 SEED 토큰으로 시작해 Toss 토큰, Threads 모양, 소프트 서피스로 세 번 바뀌었습니다.
    - 바뀔 때마다 이미 만든 화면을 전부 다시 칠했습니다.
  - **화면 흐름**
    - 댓글 입력은 별도 화면에서 게시글 화면으로, 다시 모달로 옮겼습니다.
    - 인증 화면은 2단 카드 슬라이드부터 여러 번 고쳤습니다.
  - **데이터 구조**
    - 아이디와 별명을 따로 받다가, 프로필 편집이 생기자 사람을 부르는 이름이 둘이 되어 아이디 컬럼을 지웠습니다.
    - 이미 배포된 DB라 마이그레이션을 두 번으로 나눠야 했습니다.
  - **지원 화면 폭**
    - PC 기준으로만 만들어 모바일에서 가로 스크롤이 생겼습니다.
    - 뼈대와 인증 화면을 나중에 다시 짰습니다.

- **반대로 효과를 본 경험**
  - 디자인 리뉴얼 때는 `docs/DESIGN.md` 명세와 6단계 계획을 먼저 확정했습니다.
  - 단계 사이에 겹치는 파일이 없어 3~6단계를 병렬로 진행할 수 있었습니다.

- **개선 방향**
  - 구현 전에 디자인 기준, 화면 목록과 흐름, 데이터 구조, 지원 화면 폭을 먼저 확정하겠습니다.
  - 이 네 가지를 채우고 계획을 승인받아야 구현으로 넘어가는 단계를 스킬로 만들어 하네스에 넣겠습니다.
  - 기획이 바뀌는 비용을 최소화하기 위해, 바뀌는 일을 문서 단계에서 처리하려고 합니다.

### 2. 메일 인증을 붙이겠습니다.

- **아쉬운 점**
  - Supabase 기본 메일 발송은 Supabase에 등록된 팀원 주소로만 가입 메일을 보낼 수 있어, 이메일 확인 옵션을 비활성화했습니다.
  - 그래서 지금은 이메일 주인인지 확인하지 않습니다.
    - 남의 이메일로 가입할 수 있습니다. 주인이 나중에 가입하려 하면 이미 쓰인 주소라 막힙니다.
    - 없는 이메일로 계정을 여러 개 만들 수 있습니다.

- **실제 서비스는 어떻게 하나**
  - Supabase 공식 문서도 기본 메일 발송은 테스트용이고, 실제 서비스에는 외부 메일 서버(SMTP)를 연결하라고 안내합니다.
    - 기본 메일 발송은 팀원 주소로만, 시간당 2통까지만 보내며 전달 보장이 없습니다.
    - Resend, AWS SES, Postmark, SendGrid 같은 메일 발송 서비스를 연결하면 누구에게나 보낼 수 있습니다.
    - 자기 도메인으로 보내고 SPF, DKIM, DMARC를 설정해 메일이 스팸함으로 가지 않게 합니다.

- **개선 방향**
  - 메일 발송 서비스와 도메인 인증을 연결해 가입 확인 메일을 켜겠습니다.
  - 가입 뒤 "메일함을 확인해 주세요" 안내 화면과 비밀번호 재설정을 함께 붙이겠습니다.

### 3. E2E의 로컬 실행도 테스트 DB로 분리하겠습니다.

- **아쉬운 점**
  - E2E는 PR마다 CI에서 러너 안에 띄운 테스트용 Supabase에 대고 돌고, 확인도 그 결과로 합니다.
  - 하지만 개발자 컴퓨터에서 `npm run test:e2e`로 돌리면 실제 서비스 DB를 써서, 한 번 돌 때마다 빈 계정 두 개가 남습니다.
  - 그래서 지금은 로컬 실행을 CI 실패를 재현할 때만 쓰도록 막아 두었고, 흐름을 고치면 결과를 보기까지 푸시 후 몇 분을 기다려야 합니다.

- **개선 방향**
  - 로컬에서도 CI처럼 Docker로 Supabase를 띄워 테스트 DB를 분리하겠습니다.
  - CI가 이미 같은 방식으로 돌고 있어, 로컬 실행 명령과 환경변수 전환만 더하면 됩니다.

### 4. 컴포넌트 단위 테스트를 더하겠습니다.

- **아쉬운 점**
  - 테스트를 로직과 화면 흐름 두 층으로만 나누고, 그 사이의 컴포넌트 층을 고려하지 못했습니다.
  - Vitest는 `lib/utils`와 `lib/services`의 함수만 테스트하고, E2E는 요구 기능 경로 하나만 지납니다. 가짜 DOM이 설정돼 있지 않아 컴포넌트를 렌더링해 볼 수 없습니다.
  - `AGENTS.md`는 컴포넌트마다 로딩, 비활성, 누름, 키보드 포커스 네 상태를 요구하지만, 지금은 이를 작업할 때 Playwright MCP로 한 번 열어 보고 리뷰가 보는 것으로만 지킵니다. 나중에 코드가 바뀌어 상태 하나가 빠져도 자동으로 잡히지 않습니다.

- **개선 방향**
  - Vitest에 가짜 DOM과 Testing Library를 붙여 여러 화면이 같이 쓰는 `components/ui/`부터 테스트하겠습니다. 버튼, 글쓰기 모달, 입력칸의 네 상태를 먼저 확인합니다.
  - `verify`와 CI가 이미 Vitest를 돌리고 있어, 테스트 파일만 더하면 PR마다 함께 돕니다.
