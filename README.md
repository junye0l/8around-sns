# 8around SNS

## 프로젝트 개요 및 배포 URL

생각을 짧게 나누는 SNS입니다. Claude Code와 함께 설계부터 배포까지 진행했습니다.

- **배포:** [https://8around-new-sns-beta.vercel.app](https://8around-new-sns-beta.vercel.app)
- **체험 순서:** 회원가입 → 글 작성 → 댓글 → 답글 → 다른 사람 프로필에서 팔로우 → 팔로잉 탭
(가입하면 바로 로그인됩니다. 메일 인증은 없습니다)

## 로컬 실행 방법

동작 확인은 배포 URL에서 해 주세요. 실행에는 Supabase 계정이 필요합니다.

```bash
Node 20.11 이상.

계정 없이 검사만 돌리기 (린트, 타입, 테스트, 규칙 검사)
npm install
npm run verify

직접 실행하기 (Supabase 프로젝트 필요, 대시보드에서 Confirm email 끄기)
cp .env.example .env.local
npm run db:link
npm run db:push
npm run dev
```

## 하네스 구성 설명

### 풀려고 한 문제

AI 에이전트와 며칠 동안 작업하면 세 가지 문제가 반복됩니다.

1. **세션이 바뀌면 맥락이 사라집니다.** 어제 합의한 규칙을 오늘은 모릅니다.
2. **코드만 보고 "될 겁니다"라고 보고합니다.** 실제로 화면을 열어보지 않습니다.
3. **갈림길에서 혼자 정하고 진행합니다.** 나중에 보면 왜 그렇게 했는지 남아 있지 않습니다.

그래서 규칙은 문서로 남기고, 그중 AI가 확인할 수 있는 것은 스크립트로 옮겼습니다. 사람의 기억이 아니라 저장소가 품질을 지키도록 하는 것이 목표였습니다.

### 구성


| 장치                                              | 하는 일                                                | 왜 필요했나                                                                                        |
| ----------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| [AGENTS.md](AGENTS.md)                          | 폴더 구조, 스타일, 규칙 16개, 커밋과 브랜치 규칙                      | 규칙의 출처를 하나로 두어 AI와 사람이 같은 문서를 읽게 했습니다. `CLAUDE.md`는 이 파일을 가리키기만 합니다                           |
| `npm run verify`                                | 린트, 타입 검사, 테스트, 규칙 검사를 한 번에 실행                      | AI에게 기억시킬 것을 "커밋 전에 이것 하나"로 줄였습니다                                                             |
| [규칙 검사 스크립트](scripts/harness-check.mjs)         | 토큰 밖의 스타일 값, 쓰지 않는 색 토큰, 로딩·404 화면 누락, 깨진 문서 링크를 검사 | 문서에만 적힌 규칙은 읽고 지켜야만 효과가 있습니다. 기계가 볼 수 있는 규칙은 기계에게 맡겼습니다                                       |
| [CI](.github/workflows/ci.yml)                  | PR마다 verify와 빌드 실행                                  | 로컬에서 통과하면 CI도 통과하도록 같은 명령을 씁니다                                                                |
| [AI 코드 리뷰](.github/workflows/claude-review.yml) | PR을 열면 Claude가 `AGENTS.md` 기준으로 리뷰                  | 스크립트가 못 보는 것(버그, 이미 있는 함수를 또 만든 것, 근거 없는 값)을 봅니다. 기계가 이미 보는 항목은 리뷰에서 빼 같은 지적이 두 번 나오지 않게 했습니다 |
| [PR 템플릿](.github/PULL_REQUEST_TEMPLATE.md)      | 무엇을, 어떻게, 왜, 트레이드오프                                 | 해당 없는 항목에는 "없음"을 쓰게 해서 빠뜨린 것과 없는 것을 구분합니다                                                     |
| `/pr`, `/pr-review` 스킬                          | PR 생성 절차, 리뷰 대응 절차                                  | 리뷰 지적을 그대로 따르지 않고 먼저 코드에서 확인한 뒤 고치거나 근거를 들어 반박하게 했습니다                                         |
| Playwright MCP                                  | AI가 브라우저를 열어 클릭하고 스크린샷과 콘솔을 확인                      | "될 겁니다" 대신 "눌렀더니 이게 보였다"로 보고하게 했습니다                                                           |
| [결정 기록](docs/decisions/README.md)               | 갈림길마다 선택지, 고른 것, 버린 이유, 대가                          | 코드에는 고른 것만 남습니다. 다음 세션이 같은 논의를 반복하지 않게 했습니다                                                   |


### AGENTS.md 작성 항목

[AGENTS.md](AGENTS.md)에 적은 16개 항목입니다. (에이전트)가 붙은 항목은 AI가 작업할 때 지키는 항목이고, 나머지는 사람과 AI가 함께 지킵니다.


| 항목                                      | 왜 넣었나                                               | 무엇을 지키나                                      |
| --------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| 1. 함수는 찾고, 따지고, 분리한다                    | AI는 이미 있는 함수를 찾지 않고 파일 안에 새로 쓰기 쉽습니다                | 순수 함수는 `lib/utils/`에 모이고 테스트가 붙습니다           |
| 2. 같은 것을 두 번 만들지 않는다                    | 비슷한 컴포넌트가 두 벌 생기면 한쪽만 고쳐져 화면이 어긋납니다                 | 컴포넌트와 로직이 한 곳에만 있습니다                         |
| 3. 사실은 한 곳에만 적는다                        | 같은 내용이 두 곳에 있으면 결국 하나가 낡습니다                         | 스키마, 타입, 디자인 토큰, 개발 지침, 일정마다 출처가 하나입니다       |
| 4. 근거 없이 코드를 쓰지 않는다                     | "보통 이렇게 합니다"로 쓴 코드는 이 프로젝트에 맞는지 알 수 없습니다            | 모든 판단의 근거가 `파일:줄`이나 실행 결과로 남습니다              |
| 5. 사실만 보고한다 (에이전트)                      | AI는 실행하지 않고도 "될 겁니다"라고 보고합니다                        | 테스트 결과와 동작 여부가 실제 출력으로 보고됩니다                 |
| 6. 지시받기 전까지 임의로 진행하지 않는다 (에이전트)         | AI가 갈림길에서 혼자 정하면 방향이 제 의도와 달라집니다                    | 방향은 사람이 정하고, AI는 선택지와 추천을 제시합니다              |
| 7. 사용자 환경을 건드리는 명령은 먼저 묻는다 (에이전트)       | 권한을 좁히는 DB 변경을 묻지 않고 적용했다가 배포된 서비스의 좋아요 수가 틀어졌습니다   | 개발 서버, 원격 DB, 푸시, 패키지 설치가 사람의 승인 없이 바뀌지 않습니다 |
| 8. 스키마가 타입의 출처다                         | 손으로 쓴 타입과 실제 컬럼이 어긋나면 런타임에서만 터집니다                   | DB 타입은 마이그레이션에서 생성되어 항상 스키마와 같습니다            |
| 9. 검증은 신뢰 경계에서, 권한은 RLS에서               | 브라우저 검증은 요청을 직접 보내면 뚫리고, 액션마다 권한을 확인하면 빠지는 경로가 생깁니다 | 입력은 서버가 검증하고, 소유권은 DB가 모든 경로에서 막습니다          |
| 10. 화면은 상태 네 가지가 없으면 미완성이다              | 성공 경로만 만들면 로딩, 빈 목록, 없는 주소, 에러에서 화면이 깨집니다           | 모든 화면에 로딩, 빈 상태, 없음, 에러 처리가 있습니다             |
| 11. 한 번에 한 기능                           | 화면을 다 만들고 데이터를 나중에 붙이면 마지막에 통합 문제가 몰립니다             | PR 하나가 기능 하나라서 리뷰와 되돌리기가 쉽습니다                |
| 12. `.env`, `.env.local`을 열지 않는다 (에이전트) | AI가 읽은 값은 대화, 로그, 커밋 어디에든 옮겨질 수 있습니다                | 시크릿 값이 대화 기록과 저장소에 남지 않습니다                   |
| 13. 규칙이나 구조가 바뀌면 문서를 고친다                | 낡은 문서를 읽은 다음 세션의 AI는 틀린 내용을 따릅니다                    | 문서가 항상 현재 코드와 맞습니다                           |
| 14. 갈림길은 기록한다                           | 코드에는 고른 것만 남아, 버린 선택지와 이유가 사라집니다                    | 같은 논의를 반복하지 않고, 결정을 뒤집을 때 이유를 추적할 수 있습니다     |
| 15. 주석은 TSDoc으로 쓰고 사실만 적는다              | 주석이 길고 판단까지 담으면 코드와 어긋났을 때 무엇을 믿을지 모릅니다             | 주석은 동작과 제약만 담고, 판단의 이유는 결정 기록에 있습니다          |
| 16. 화면은 열어서 확인한다 (에이전트)                 | 코드만 읽고는 실제 화면에서 깨지는 것을 알 수 없습니다                     | Playwright로 누르고 본 결과(스크린샷, 콘솔)가 완료의 근거가 됩니다  |


이 중 AI가 확인할 수 있는 것은 `npm run verify`가 커밋 전에 검사하고, 나머지는 PR의 AI 리뷰와 `/pr`, `/pr-review` 스킬이 봅니다.

### 하네스가 실제로 잡은 것

- **문서가 조용히 되돌아간 사고**
  - 계획 문서를 고쳐 커밋했는데, 에디터에 열려 있던 옛 버전이 저장되면서 내용이 롤백되었습니다.  
  테스트는 문서를 보지 않아 통과했고, AI 리뷰가 PR에서 잡았습니다. 그 뒤로 문서 수정은 커밋 전에 main과 비교해 범위를 확인합니다.
- **리뷰가 돌지 않았는데 초록불이던 문제**
  - 워크플로 파일을 고친 PR에서는 GitHub Action이 리뷰 실행을 거부하는데,  
  체크 표시는 초록이었습니다. 이 경우 "사람이 봐야 한다"는 댓글을 자동으로 남기게 고쳤습니다.
- **DB 변경이 배포된 서비스를 깨뜨린 사고**
  - 좋아요 조회 권한을 좁히는 마이그레이션을 먼저 적용했더니, 아직 옛 코드가 돌던 배포본의 좋아요 수가 틀어졌습니다.  
  이후 규칙을 바꿨습니다. DB 적용은 건마다 묻고, 컬럼 삭제처럼 좁히는 변경은 "넓히기 → 코드 배포 → 좁히기" 세 단계로 나눕니다.

## 구현 중 내린 주요 기술적 의사결정과 트레이드오프

### 1. 권한 검사는 서버 코드가 아니라 DB 정책(RLS)에 둔다

- **상황:** "이 글이 내 글인가"를 수정, 삭제, 댓글 액션마다 확인하면 기능이 추가될 때 반드시 빠지는 경로가 생깁니다.
- **해결방법:** Postgres RLS 정책 한 곳에 쓰고, 서버 코드에는 같은 검사를 두지 않았습니다.
- **트레이드오프:** 서버 코드만 봐서는 권한이 보이지 않아 `supabase/migrations/`를 함께 읽어야 합니다.

### 2. 좋아요 목록이 남에게 보이던 문제를 해결.

- **상황:** "좋아요한 글" 화면을 만들다가, 공개 키로 URL로 직접 접속한다면, **다른 사람이 좋아요한 글 목록**도 조회된다는 것을 발견했습니다. 화면은 이 조회를 부르지 않아서 눈에 띄지 않던 경로였습니다.
- **해결책:** 조회 권한을 본인으로 좁히면 좋아요 수를 셀 방법이 사라집니다. 
  - (A) 수만 돌려주는 DB 함수
  - (B) 게시글 테이블에 카운터 컬럼과 트리거
- **해결방법:** A. 카운터 방식은 기존 데이터를 채우고, 동시 요청을 처리하고, 값이 어긋났을 때 복구하는 일까지 따라옵니다.
- **트레이드오프:** 글마다 좋아요를 세므로 좋아요가 아주 많아지면 느려집니다.

### 3. 불필요한 인증 서버 요청

- **상황:** 배포 환경이 느려 원인을 따라가 보니, 응답 시간이 Server와 Supabase 사이 왕복 횟수에 비례했습니다. 한 요청 안에서 세션 확인을 두 번 하고 있었습니다.
- **해결방법:** 두 번째 세션 확인은 네트워크 없이 JWT 서명만 검증하도록 바꿨습니다. 팔로잉 피드는 ㅜ이 세 번 나눠 읽던 것을 DB 함수 하나로 합쳤습니다.
- **제외된 방법:** 첫 확인 결과를 헤더로 넘기는 방법. 검증은 한 곳으로 모이지만 헤더는 위조할 수 있습니다.
- **트레이드오프:** Supabase 프로젝트가 비대칭 키를 써야 이득이 있어서, 키 방식을 먼저 확인했습니다.

### 4. 버튼 중복 호출

- **상황:** 브라우저에서 직접 요청 수를 셌습니다. 보통 더블클릭은 괜찮았지만, 아주 짧은 간격의 클릭 두 번은 글쓰기, 댓글, 팔로우, 로그인 모두 요청이 두 번 갔습니다.
- **해결책**
  - (A) 화면이 다시 그려지기 전에 즉시 막는 클라이언트 잠금.
  - (B) 서버에서 중복 키로 거르기
- **해결방법**: **(A)** 로 결정 **(B)** 는 테이블마다 제약과 키 수명 정책이 필요해 이 규모에는 과했습니다.
- **트레이드오프**
  - 중복 방지 잠금은 브라우저 탭 안에만 있습니다. 개발자 도구나 스크립트로 요청을 직접 두 번 보내거나,  
  두 탭에서 동시에 제출하면 서버는 둘 다 저장합니다. 서버에서 막으려면 요청마다 고유 키와 DB 제약이 필요한데, 같은 글을 두 번 쓰는 것과 결과가 같아 데이터가 깨지지는 않으므로 이 비용을 들이지 않았습니다.

## 시간이 더 있었다면 개선했을 부분

### 1. 기획에 더 시간을 쓰겠습니다

- **아쉬운 점:** 요구 기능을 빠르게 구현하려고 기획을 가볍게 잡고 시작했더니, 작업 중에 기획이 계속 바뀌었습니다.  
기술적인 선택, 디자인, 페이지별 변경사항 등 기획과 구현을 번갈아 다시 하면서 작업 속도가 느려졌습니다.
- **실제로 바뀐 것:** 착수 전에 정하지 않은 네 가지가 작업 중에 다시 결정됐습니다.
  - **디자인 기준.** 당근 SEED 토큰으로 시작해 Toss 토큰 -&gt; Threads 모양, 소프트 서피스로 세 번 바뀌었습니다. 바뀔 때마다 이미 만든 화면을 전부 다시 칠했습니다.
  - **화면 흐름.** 댓글 입력은 별도 화면에서 게시글 화면, 다시 모달로 옮겼습니다. 인증 화면은 2단 카드 슬라이드부터 여러 번 고쳤습니다.
  - **데이터 구조.** 아이디와 별명을 따로 받다가, 프로필 편집이 생기자 사람을 부르는 이름이 둘이 되어 아이디 컬럼을 지웠습니다. 이미 배포된 DB라 마이그레이션을 두 번으로 나눠야 했습니다.
  - **지원 화면 폭.** PC 기준으로만 만들어 모바일에서 가로 스크롤이 생겼고, 뼈대와 인증 화면을 나중에 다시 짰습니다.
- **반대로 효과를 본 경험:** 디자인 리뉴얼 때는 `docs/DESIGN.md` 명세와 6단계 계획을 먼저 확정했습니다. 단계 사이에 겹치는 파일이 없어 3~6단계를 병렬로 진행할 수 있었습니다.
- **개선 방향:** 구현 전에 디자인 기준, 화면 목록과 흐름, 데이터 구조, 지원 화면 폭을 먼저 확정하겠습니다. 이 네 가지를 채우고 계획을 승인받아야 구현으로 넘어가는 단계를 스킬로 만들어 하네스에 넣겠습니다.  
기획이 바뀌는 비용을 최소하기 위해서 문서단계에서 처리하려고 합니다.

### 2. 메일 인증을 붙이겠습니다

- **아쉬운 점:** Supabase 기본 메일 발송은 Supabase에 등록된 팀원 주소로만 가입 메일을 보낼 수 있어, 이메일 확인 옵션을 비활성화했습니다.
그래서 지금은 이메일 주인인지 확인하지 않습니다.
  - 남의 이메일로 가입할 수 있습니다. 주인이 나중에 가입하려 하면 이미 쓰인 주소라 막힙니다.
  - 없는 이메일로 계정을 여러 개 만들 수 있습니다.
- **실제 서비스는 어떻게 하나:** Supabase 공식 문서도 기본 메일 발송은 테스트용이고, 실제 서비스에는 외부 메일 서버(SMTP)를 연결하라고 안내합니다.
  - 기본 메일 발송은 팀원 주소로만, 시간당 2통까지만 보내며 전달 보장이 없습니다.
  - Resend, AWS SES, Postmark, SendGrid 같은 메일 발송 서비스를 연결하면 누구에게나 보낼 수 있습니다.
  - 자기 도메인으로 보내고 SPF, DKIM, DMARC를 설정해 메일이 스팸함으로 가지 않게 합니다.
- **개선 방향:** 메일 발송 서비스와 도메인 인증을 연결해 가입 확인 메일을 켜고, 가입 뒤 "메일함을 확인해 주세요" 안내 화면과 비밀번호 재설정을 함께 붙이겠습니다.
