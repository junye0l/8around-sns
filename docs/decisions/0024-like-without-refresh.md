# 0024. 좋아요는 화면을 다시 그리지 않는다

- 상태: 확정
- 날짜: 2026-09-13
- 대체: [0021](0021-like-optimistic.md)의 "성공하면 `refresh`가 같은 값을 가져온다" 부분

## 맥락

좋아요 액션이 끝나면 `refresh()`로 화면 전체를 서버에서 다시 그려 보냈다. 추천 피드면
글 50개와 작성자, 댓글 수, 좋아요 수를 다시 읽고 RSC 페이로드로 실어 보낸다(dev 실측 33 KB).
버튼은 이미 낙관적으로 바뀌어 있어(결정 0021) 이 응답을 기다리는 사람이 없다.

렌더링 진단에서 배포의 시간이 함수 ↔ Supabase 왕복 수에 곱해진다는 것이 드러났다.
좋아요 한 번이 왕복 3개짜리 화면 렌더를 하나 더 만들고 있었다.

## 선택지

**A. 그대로 둔다** — 성공 뒤 `refresh()`

- 화면에 뜨는 값이 항상 DB의 값이다. 다른 사람이 그 사이 누른 좋아요도 같이 온다
- 누를 때마다 글 50개를 다시 읽는다. 글이 500개면 그대로 열 배다

**B. `refresh()`를 빼고 성공한 값을 버튼이 확정한다**

- 액션 응답이 결과 한 줄이다. 서버는 좋아요 행 하나만 만지고 끝난다
- 다음 렌더까지 다른 사람의 좋아요는 안 보인다. 그 사람이 화면을 옮기거나 다른 액션이
  화면을 다시 그릴 때 따라온다 — 지금도 그 사이 값은 낡아 있었다
- `useOptimistic`의 기준값을 props가 아니라 확정 상태로 두어야 한다. props는 액션이
  끝나도 그대로라, 기준이 props면 버튼이 누르기 전 값으로 돌아간다

**C. 액션이 새 수를 세어 돌려준다**

- 서버 값이 화면에 온다
- 좋아요 행을 쓰고 나서 수를 한 번 더 읽는다. 왕복이 하나 더 붙는데, 낙관적으로 바꾼
  값과 거의 항상 같은 수다

## 결정

**B.** 액션이 하는 일이 좋아요 행 하나인데 응답이 화면 전체일 이유가 없다.

`LikeButton`이 서버가 마지막으로 확인해 준 값(`known`)을 들고, `useOptimistic`의 기준으로
쓴다. 성공하면 `known`을 앞당기고, 실패하면 `known`이 그대로라 거기로 돌아온다.
props가 바뀌면(다른 액션이 화면을 다시 그린 경우) `known`을 props로 다시 맞춘다 —
렌더 중에 상태를 맞추는 React의 "props에서 파생한 상태" 방식이다.

## 따라온 것

- 좋아요 액션의 응답이 화면 전체(dev 33 KB)에서 결과 한 줄로 줄었다
- 다른 진입점(작성, 수정, 삭제, 댓글, 팔로우)은 그대로 `refresh()`다. 그것들은 목록 자체가
  바뀌므로 화면을 다시 그리는 것이 맞다
- **빠르게 두 번 누르면 응답 순서가 클릭 순서와 다를 수 있다.** 마지막으로 누른 클릭의
  응답만 `known`을 확정하고 앞선 응답은 버린다. DB 쪽 순서까지 보장하지는 않는다 —
  두 요청이 DB에 거꾸로 닿으면 화면과 DB가 다음 렌더까지 어긋난다. 전에는 `refresh()`가
  매번 DB를 다시 읽어 이걸 지워 줬다. 창은 왕복 하나 길이이고, 그 안에 두 번 누르는 경우다
- `LikeButton`에 상태가 둘 늘었다. 하나는 확정값, 하나는 마지막으로 본 props다.
  `useEffect`로 동기화하지 않은 이유는 한 렌더 늦게 맞춰지는 사이에 옛 값이 한 번 보이기 때문이다
