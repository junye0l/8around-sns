# 0031. 누가 좋아요했는지는 본인만 보고, 수는 계산 컬럼이 준다

- 상태: 확정
- 날짜: 2026-09-14
- 대체: [0020](0020-post-likes.md)의 "수는 `post_likes(count)`로 세어 온다"

## 맥락

좋아요한 글 피드(PR #65)를 만들면서 `post_likes`에서 내 id로 거르는 조회가 생겼다. 그런데
`0003_post_likes.sql`의 "좋아요는 누구나 본다"가 `using (true)`라 같은 조회에 다른 사람 id를 넣으면
그 사람이 좋아요한 글 목록이 나온다. 화면이 부르지 않아도 anon 키로 요청을 직접 보내면 된다.
사용자가 "좋아요한 글"은 개인 모음으로 보고 막기로 했다.

select를 본인 행으로 좁히면 `lib/queries/post.ts`의 `post_likes(count)` 임베드도 내 좋아요만 센다.
수를 어디서 줄지가 갈림길이었다.

## 선택지

**A. 계산 컬럼 함수 `like_count(post)`, security definer**

- `0004_post_liked_by_viewer.sql`의 `liked_by_viewer`와 같은 모양이다. 스키마 변경은 함수 하나다
- RLS를 건너뛰어 세지만 돌려주는 것은 수뿐이라 누가 눌렀는지는 새지 않는다
- 글마다 세므로 좋아요가 아주 많아지면 비용이 커진다. 기본키 앞부분(`post_id`)이 받는다

**B. `posts`에 카운터 컬럼과 트리거**

- 읽기가 가장 싸다
- 기존 행 백필, 트리거의 동시성, 컬럼과 실제 행이 어긋났을 때의 복구까지 다뤄야 한다

## 결정

**A.** 사용자가 골랐다.

같이 정한 값:

- **새 정책 "본인 좋아요만 본다".** `using ((select auth.uid()) = user_id)`. insert, delete 정책은 그대로다
- **`liked_by_viewer`는 고치지 않는다.** 원래 본인 행만 보므로 새 정책에서도 같은 값이다
- **`listLikedFeed`(PR #65)도 고치지 않는다.** 본인 행만 읽는다

## 비용

- 원격 DB에 정책을 먼저 적용하므로, 이 변경이 머지되기 전까지 `post_likes(count)`로 세는 배포본은
  좋아요 수가 보는 사람 자신의 좋아요(0 또는 1)로 보인다
- `security definer` 함수가 하나 늘었다. 함수 본문이 바뀌면 권한을 다시 검토해야 한다
