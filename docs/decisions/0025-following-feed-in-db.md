# 0025. 팔로잉 피드는 DB가 한 번에 거른다

- 상태: 확정
- 날짜: 2026-09-13

## 맥락

팔로잉 피드는 화면 중 가장 깊은 순차 왕복을 갖고 있었다. 프록시의 세션 확인 뒤에
내 id → 팔로우 목록 → 그 목록으로 글, 세 번을 차례로 갔다. 렌더링 진단에서 배포의
시간이 이 왕복 수에 곱해진다는 것이 드러났다.

원래 그렇게 짠 이유는 `lib/queries/post.ts`의 옛 주석에 있다 — PostgREST가 서브쿼리를
못 받고, 임베드로 내려가면 필터가 한 단 더 깊어진다.

## 선택지

**A. 그대로 둔다** — 앱이 세 번 읽는다

- 마이그레이션이 없다
- 순차 3단이 그대로다. 함수를 서울로 옮겨도 다른 화면보다 한두 왕복 깊다

**B. 프로필 조회와 나란히 던진다** — 코드만 바꾼다

- 내 id는 `getClaims()`로 네트워크 없이 나오므로(결정 0023) 팔로우 목록 → 글 두 번만 남고,
  프로필 조회와 나란히 갈 수 있다. 3단 → 2단
- 팔로우 목록을 앱으로 가져와 다시 보내는 왕복은 남는다

**C. DB 함수 하나가 거른다** — `following_posts()`, `setof posts`

- 한 번이다. 보는 사람 id를 앱이 넘기지 않는다 — 0004의 `liked_by_viewer`와 같이
  요청의 JWT에서 `auth.uid()`를 꺼낸다
- `setof posts`라 PostgREST가 테이블처럼 다룬다. 추천 피드와 같은 select 문자열, 임베드,
  계산 컬럼, 정렬, 개수가 그대로 붙는다. 앱 코드에 두 벌이 생기지 않는다 (규칙 2)
- 마이그레이션이 하나 늘고 결정 기록이 필요하다 (규칙 8, 14)

## 결정

**C.** 왕복 하나 차이지만 이 화면이 가장 깊었고, 함수는 이미 있는 방식(0004)의 반복이다.
`security invoker`라 RLS "게시글은 누구나 본다"가 그대로 적용된다.

빈 화면의 두 문구("팔로우한 사람이 없다" / "팔로우했는데 글이 없다")를 가르는 데 필요한
"팔로우한 사람이 있는가"는 글이 하나도 없을 때만 따로 묻는다. 매번 물으면 아낀 왕복을
도로 쓰는 셈이다.

## 따라온 것

- `FollowingFeed` 타입이 사라졌다. 질의는 글 목록만 돌려주고, 두 문구를 가르는 것은
  `app/following/page.tsx`가 한다
- `listFollowingIds`는 그대로 남는다. 팔로잉 목록 화면과 위의 빈 경우 판정이 쓴다
- 팔로우한 사람이 수천을 넘으면 `in (select …)`의 비용이 보이기 시작한다. 그때 `join`으로
  바꾼다 — 지금은 `posts_author_id_idx`가 받는다
