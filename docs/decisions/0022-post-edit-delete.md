# 0022. 내 글을 수정하고 지운다

- 상태: 일부 대체됨 → [0037](0037-comment-edit-delete.md)
- 날짜: 2026-09-12

## 맥락

요구 기능 6개에 수정과 삭제는 없다. 좋아요와 같은 경로로 사용자가 요청해서 범위에
들어왔다 — 게시글 오른쪽 위에 더보기 아이콘을 두고 거기서 수정과 삭제를 한다.

스키마에는 이미 자리가 있다. `supabase/migrations/0001_init.sql:137-144`가
"본인 게시글만 수정한다"와 "본인 게시글만 지운다"를 처음부터 들고 있었고,
쓰는 쪽이 없어서 안 쓰이고 있었을 뿐이다. 마이그레이션을 더하지 않는다.

댓글은 범위 밖으로 둔다. 사용자가 말한 것은 게시글이다.

## 선택지

### 누가 내 글인지 가리는 방법

**A. 별명으로 가린다** — `post.author.username === viewerUsername`

- 질의도 타입도 그대로다. 화면은 이미 작성자 별명을 들고 있다
- 별명은 유일하다(`supabase/migrations/0001_init.sql:14`). 두 사람이 같은 값을 가질 수 없다

**B. 질의에 `author_id`를 더하고 id로 가린다**

- id는 별명이 바뀌어도 그대로다
- `POST_SELECT`, `FeedPost`, 네 화면이 같이 바뀐다. 별명 변경 기능은 범위 밖이라
  지금 막을 것이 없다

### 삭제를 확인할 것인가

**C. 바로 지운다** — 메뉴에서 고르는 순간

- 누르는 횟수가 하나 적다
- 되돌릴 수 없다. 메뉴는 포인터 밑에서 열리므로 잘못 고르기 쉬운 자리다

**D. 모달로 한 번 묻는다**

- 되돌릴 수 없는 것 앞에 문이 하나 선다. 댓글과 좋아요가 같이 사라진다는 것도 여기서 말한다
- 화면 하나가 늘어난다. 모달과 버튼은 이미 있는 것을 쓴다

## 결정

**A와 D.**

A는 지금 없는 기능(별명 변경)을 위해 네 화면을 고치지 않는다는 뜻이다. 별명을 바꾸는
기능이 생기면 그때 B로 옮긴다 — 그때는 옮길 이유가 생긴 뒤다.

D는 삭제가 cascade로 댓글과 좋아요까지 지우기 때문이다
(`supabase/migrations/0001_init.sql:77`, `0003_post_likes.sql:7`). 지운 사람이 자기 글
하나만 사라진다고 생각하면 안 된다.

## 따라온 것

- **소유권 체크를 앱에 두지 않는다.** `updatePost`와 `deletePost`는 작성자 id를 받지
  않는다. RLS가 남의 글을 0행으로 만들고, 서비스는 `select()`로 받은 행이 없으면
  그것을 문구로 바꾼다. 규칙 9 그대로다. 메뉴를 내 글에만 그리는 것은 친절함이지 방어가 아니다
- **`ComposeDialog`가 밖에서 열릴 수 있게 됐다.** 메뉴 항목은 고르는 순간 사라지므로
  그 안에 트리거를 둘 수 없다. `open`과 `onOpenChange`를 받아 부르는 쪽이 상태를 든다.
  트리거를 주는 기존 사용처는 그대로다
- **수정 모달은 새 글 모달과 같은 것이다.** `POST_COMPOSE`를 펴고 액션, 버튼 문구,
  제목만 덮는다. 입력칸이 두 벌이 되지 않는다 (규칙 2)
- **상세 화면에서 지우면 404가 뜬다.** 글이 사라진 자리에 그대로 서 있기 때문이고,
  그건 사실이다. 목록으로 돌려보내려면 액션이 어디서 불렸는지 알아야 하는데 그 값을
  만들지 않았다. 불편하다는 말이 나오면 그때 리다이렉트를 더한다
- **확인 모달은 입력 모달과 모양이 다르다.** 물음과 답 둘뿐이라 위쪽 제목줄을 두지
  않고 질문이 곧 제목이 된다. 아래 한 줄에 취소와 삭제가 같은 너비로 나란히 서고 1px이
  가른다. 껍데기(어두운 바탕, 테두리 두른 흰 면)는 `DialogShell`로 빼서 둘이 같이 쓴다
- **버튼에 `danger` 변형을 만들지 않았다.** 확인 모달의 "삭제"는 `Button`이 아니라
  줄 절반을 채우는 글자다. 빨강은 `--color-danger`가 "파괴적 동작"에 주는 색이고,
  메뉴 항목의 삭제와 같다
