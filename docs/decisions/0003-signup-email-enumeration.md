# 0003. 가입 시 이메일 중복을 그대로 알린다

- 상태: 확정
- 날짜: 2026-09-11

## 맥락

가입 폼에서 이미 가입된 이메일을 넣으면 "이미 가입한 이메일이에요"가 뜬다.
이건 그 주소의 **가입 여부를 확인해 주는 것**이다 — 계정 열거(account enumeration)다.

로그인 화면은 이미 막아뒀다. `invalid_credentials`를 필드에 붙이지 않고
"이메일 또는 비밀번호가 맞지 않아요" 한 줄로 통일한다(`lib/services/auth.ts`).

별명 중복은 문제가 아니다. `프로필은 누구나 본다` 정책이 `using (true)`라
(`supabase/migrations/0001_init.sql:117-119`) 별명 목록은 원래 공개다.

## 선택지

**A. 그대로 알린다**
- 이미 가입한 사람이 왜 막혔는지 즉시 안다. 이 사람이 압도적 다수다
- 특정 주소의 가입 여부가 확인된다

**B. 문구를 뭉갠다** ("가입하지 못했어요. 입력한 내용을 다시 확인해 주세요")
- 힌트를 주지 않는다
- 진짜 재가입자가 이메일·별명·비밀번호 중 무엇을 고쳐야 할지 알 수 없다

## 결정

**A.**

## 이유

문구를 뭉개도 통로가 닫히지 않는다. 공격자는 가입을 **시도해서 성공 여부**로 여전히 알아낸다.
B는 정상 사용자에게 막다른 길을 주면서 공격자에게는 난이도만 조금 올린다.

메일을 보내는 서비스는 "화면에는 성공이라 하고 기존 주인에게 시도 알림을 보내는" 수로 피한다.
[0002](0002-email-confirmation-off.md)에서 이메일 확인을 껐으므로 보낼 메일이 없다. 이 수는 못 쓴다.

실질적 방어는 요청 제한이고 Supabase에 이미 있다(`supabase/config.toml:196` `[auth.rate_limit]`).

## 비용

특정 이메일의 가입 여부가 확인된다. 표적 피싱에 쓰일 수 있다.
되돌리려면 `lib/services/auth.ts`의 `fromAuthCode`에서 case 하나를 `formError`로 옮기면 된다.
