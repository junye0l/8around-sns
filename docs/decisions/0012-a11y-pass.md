# 0012. 접근성 지적을 토큰 안에서만 고치고, 토큰 자체가 걸리는 둘은 남겨둔다

- 상태: 일부 대체됨 → [0041](0041-soft-surface.md) (남은 칸 둘)
- 날짜: 2026-09-12

## 맥락

팔로우 기능을 붙인 뒤 접근성과 성능을 병렬로 감사했다. 접근성 15건, 성능 8건이 나왔다.
Biome은 74파일 0건이었다 — 여기 나온 것은 전부 Biome이 못 보는 것들이다.
정적 JSX 모양은 보지만 대비를 계산하지 않고, 토큰을 모르고, 서버 액션 이후의 포커스를
추적하지 않는다.

지적을 셋으로 나눴다.

1. 레포 안의 값과 패턴만으로 고쳐지는 것
2. 값의 출처가 `docs/DESIGN.md`라 규칙 3·4에 걸리는 것
3. 규칙 7·13·14가 승인을 먼저 요구하는 것

## 선택지

### 로딩 중 버튼을 어떻게 막나

포커스된 요소가 `disabled`가 되면 브라우저가 포커스를 `body`로 떨어뜨린다.
서버 액션이 끝나 버튼이 살아나도 포커스는 문서 맨 위에 있다. 키보드로 팔로우를
누르면 다음 동작을 하려고 네비를 다시 지나야 한다.

**A. 그대로 두고 액션이 끝나면 포커스를 되돌린다** — `ref` + `useEffect`

- 진짜 `disabled`라 브라우저가 클릭을 확실히 막는다
- 버튼을 쓰는 곳마다 같은 코드가 붙는다. 지금 넷이고 늘어난다

**B. `aria-disabled`로 바꾸고 `onClick`에서 막는다**

- 요소가 살아 있어 포커스가 그대로 있다. 되돌릴 것이 없다
- AT에는 여전히 비활성으로 읽힌다
- 회색 처리를 `disabled:`가 못 한다. 다른 걸림쇠가 필요하다

### B를 골랐을 때 회색을 무엇이 칠하나

**C. `aria-disabled:` 유틸리티** — 의미와 모양이 같은 속성에 붙는다

- 빈 입력일 때의 진짜 `disabled`와 로딩이 같은 회색이 된다

**D. `aria-busy:` 유틸리티** — 진행 중이라는 뜻의 속성에 붙는다

- `aria-disabled`는 의미만, `aria-busy`는 모양만 맡는다. 둘이 안 겹친다
- `hover:`가 뒤에 와서 회색을 덮을 수 있다. `aria-busy:hover:`를 같이 적어야 한다

## 결정

**B + D.**

B는 고치는 자리가 `Button` 한 곳이고 호출부가 아무것도 안 바꾼다.
D를 고른 이유는 `aria-disabled`에 색까지 얹으면 "못 누른다"와 "지금 일하는 중이다"가
한 속성에 섞이기 때문이다. 생성된 CSS에서 `[aria-busy=true]` 규칙이
`:hover`보다 뒤에 오고 `[aria-busy=true]:hover`가 한 단 더 구체적인 것을 확인했다.

## 같이 고친 것

전부 레포 안의 값과 이미 쓰던 패턴만 썼다.

- 글쓰기 칸에 포커스 링. `outline-none`만 있고 대체물이 없었다. `Button`이 쓰던
  유틸리티 문자열을 그대로 옮겼다
- 인증 필드 에러에 `role="alert"`. 폼 전체 에러만 말하고 필드 에러는 조용했다.
  `lib/services/auth.ts`에는 필드 에러만 돌려주는 경로가 여섯이라, 가입이 실패해도
  아무 소리가 안 났다. hint에는 붙이지 않는다 — 화면에 뜰 때마다 읽어서 시끄럽다
- 입력칸 테두리를 `hairline`에서 `fg-muted`로. 흰 카드 위 흰 입력칸에
  `#e5e8eb` 테두리는 대비 1.23:1이라 경계가 안 보였다. `#8b95a1`은 3.04:1이고
  WCAG 1.4.11이 UI 경계에 요구하는 3:1을 넘는다. 문서 안의 값이다
- `not-found` 넷과 `error` 하나의 제목을 `p`에서 `h1`로. 헤딩이 하나도 없는 문서였다.
  헤딩 목록으로 훑으면 빈 화면으로 보인다
- 사람 목록을 `ul`/`li`로. 피드와 댓글은 `article`이라 항목 단위로 건너뛰는데
  새 목록만 빠져 있었다. preflight가 `list-style: none`과 여백 0을 이미 주므로
  모양은 그대로다
- 라우트마다 문서 제목. 전에는 전부 "8around"였다. 동적 라우트는 주소의 별명만 쓴다 —
  제목을 위해 프로필을 한 번 더 읽지 않는다
- 팔로우 버튼에 `aria-pressed`. `refresh` 뒤에 라벨만 바뀌면 포커스가 머문 채
  텍스트 노드만 교체돼 스크린리더가 지나친다
- 뒤로 버튼과 댓글 수 링크에 포커스 링. 다른 모든 인터랙티브 요소가 갖고 있었다
- `lib/queries/follow.ts`의 인덱스 주석. `follows_following_id_idx`가 정렬까지
  "그대로 받는다"고 적혀 있었는데 사실이 아니다. 필터만 받고 `created_at` 정렬은
  인덱스 밖이다. 코드에 박힌 거짓이라 규칙 4 위반이었다

## 남겨둔 것

### 답을 기다리는 둘

값의 출처가 `docs/DESIGN.md`다. 규칙 3·4가 문서에 없는 값을 지어내지 못하게 한다.

- **보조 텍스트 `#8b95a1`이 흰 바탕에서 3.04:1** (WCAG 1.4.3 AA는 4.5:1).
  모든 작성자 핸들과 시각 표시가 여기 걸린다. 문서 안의 `#4e5968`(7.35:1)로
  올리는 길이 있고, 그때 비활성 버튼 글자 2.47:1도 같이 풀린다
- **primary 버튼 흰 글자가 3.71:1.** 앱의 모든 주 동작이다. `#3182f6`도 `#ffffff`도
  문서가 직접 지정했고, 버튼 글자가 16px/600이라 큰 글자 완화에도 못 들어간다.
  `#2272eb`로 내려도 4.49:1이라 0.01 차이로 안 풀린다
- 에러 문구 `#e42939`가 4.49:1인 것도 같은 종류다. 눈으로는 차이가 없어 우선순위가 낮다

### 승인이 먼저인 것

- **미들웨어가 확인한 유저를 헤더로 내려보내기.** 페이지당 Auth 왕복이 2에서 1로,
  팔로우 클릭이 4에서 2로 준다. 들어온 `x-user-id`를 미들웨어 첫 줄에서 지우지 않으면
  헤더 위조로 남의 프로필이 렌더된다. 보안 판단이라 규칙 14 대상이고 규칙 6이 승인을 먼저 요구한다
- **tailwind-merge 빼기.** 9.3KB gz가 404 화면 포함 전 라우트에 실리는데 충돌 해소가
  한 번도 안 쓰인다. 다만 `AGENTS.md` 스타일 절이 `cn()` 사용을 명시하므로 규칙 13에 따라
  문서 수정 승인이 먼저다
- **`lib/supabase/client.ts` 삭제.** 임포트하는 곳이 없다. 파일을 지우는 것은 구조 변경이라
  규칙 13에 걸리고, `docs/PLAN.md`의 체크 항목도 같이 고쳐야 한다
- **`middleware`에서 `proxy`로 옮기기.** Next 16이 deprecated라고 경고한다.
  위 두 건이 전부 이 파일을 건드리므로 같이 옮기는 편이 낫다

### 안 고치는 쪽이 나은 것

- **`follows` 복합 인덱스.** 정렬이 인덱스를 못 받는 건 맞지만 `LIMIT 100`에
  팔로워가 세 자리를 넘을 일이 없다. 마이그레이션과 `db:push`, `types:gen` 비용이 더 크다.
  주석만 고쳤다
- **`isFollowing`을 `getProfile`에 합치기.** 왕복 하나를 아끼자고 "누구에게나 같은 쿼리"와
  "보는 사람마다 다른 쿼리"를 섞으면 나중에 캐시를 켤 때 걸림돌이 된다
- **`SideNav`를 서버 컴포넌트로.** 수 KB 대 호출부 여섯 곳의 유지보수다. 진 거래다
- **스킵 링크.** 반복 블록이 링크 셋뿐이고 AT는 `nav` 랜드마크로 이미 건너뛴다
- **`Button`의 링크 변형에 props 넘기기.** `href`가 있으면 `aria-label`이 조용히 사라진다.
  지금 호출부 넷이 다 텍스트만 써서 깨지는 곳이 없고, 고치려면 `button`과 `a`의 속성을
  가르는 타입이 필요하다. 아이콘만 있는 링크 버튼을 처음 만들 때 같이 한다
