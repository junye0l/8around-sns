# 0048. 심사 시나리오 E2E는 로컬에서 원격 DB에 대고 돌리고, 글과 팔로우만 지운다

- 상태: 일부 대체됨 → [0049](0049-e2e-ci-first.md)
- 날짜: 2026-09-15

## 맥락

요구 기능 6개를 한 줄로 지나는 E2E가 없었다. 단위 테스트(`lib/services/*.test.ts`)는 DB를 흉내 낸 가짜로 돌아
화면 흐름이 실제로 이어지는지는 보지 못한다. 실제로 답글이 0개인 댓글에서 답글 화면으로 갈 길이 없던 것을
단위 테스트는 잡지 못했다([0047](0047-reply-entry-without-replies.md)).

도구는 Playwright Test다. Vitest와 Jest는 브라우저를 띄우지 않는다.
갈림길은 어느 DB에 대고 돌리느냐와, 만든 데이터를 어디까지 지우느냐였다.
원격 Supabase는 로컬 개발, 프리뷰, 프로덕션이 함께 쓴다.

## 선택지

**어느 DB에**

- A. Docker로 띄운 로컬 Supabase. 프로덕션을 건드리지 않는다. 사용자 컴퓨터에 Docker 실행이 필요하다
- B. 원격 Supabase. 설정이 없다. 돌 때마다 실제 서비스 DB에 계정과 글이 생긴다

**어디까지 지우나** (B일 때)

- C. 글과 팔로우만 지운다. 글을 지우면 댓글과 답글은 cascade로 지워진다(`supabase/migrations/0001_init.sql:77-79`). 계정은 남는다
- D. `service_role` 키로 계정까지 지운다. RLS를 전부 우회하는 키를 테스트 환경에 둬야 한다
- E. "내 계정 삭제" DB 함수를 마이그레이션으로 연다. 요구 범위 밖의 회원 탈퇴를 프로덕션에 연다

## 결정

**로컬 실행은 B와 C.** 사용자가 골랐다.

- 실행은 로컬에서만 한다. 떠 있는 개발 서버에 붙고 서버를 띄우지 않는다(`playwright.config.ts`)
- 계정 둘을 실행 시각으로 만든다. `e2e-a-<시각>@example.com`, `e2e-b-<시각>@example.com`
- 정리는 `finally`에서 한다. 한 동작이 테스트 전체 시간을 다 쓰면 브라우저가 닫혀 정리가 돌지 못하므로
  동작 제한을 15초로 둔다. 실제로 제한이 없을 때 실패한 실행이 글을 남겼다
- CI는 B를 쓰지 않는다. PR마다 계정이 쌓이기 때문이다. GitHub Actions 러너에는 Docker가 있으므로
  CI에서는 A로 돌린다. 워크플로는 별도 PR에서 붙인다

## 비용

- 로컬에서 한 번 돌 때마다 빈 계정이 둘 남는다. 글도 팔로우도 없어 화면 어디에서도 링크되지 않는다
- 테스트가 도는 10여 초 동안 테스트 글이 실제 피드에 보인다
- 로컬(원격 DB)과 CI(빈 로컬 DB)의 데이터가 다르다
- 정상 경로 하나만 본다. 수정, 삭제, 좋아요, 권한 거절, 모바일 폭은 보지 않는다
