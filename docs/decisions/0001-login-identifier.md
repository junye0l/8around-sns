# 0001. 로그인 식별자는 이메일이다

- 상태: 확정
- 날짜: 2026-09-11

## 맥락

가입 폼에서 이메일 · 별명 · 비밀번호를 받는다. 로그인은 무엇으로 받을지 정해야 했다.
별명으로 로그인하면 가입 때 정한 이름을 그대로 쓰니 기억하기 쉽다.

## 선택지

**A. 이메일 + 비밀번호**
- 추가 코드 0줄. `signInWithPassword`를 그대로 부른다
- 사용자가 가입할 때 쓴 이메일을 기억해야 한다

**B. 별명 + 비밀번호**
- 기억하기 쉽다
- 별명 → 이메일 매핑이 필요하고 두 방법 다 문제가 있다
  - `profiles`에 email 컬럼 추가 → **안 된다.** select 정책이 `using (true)`라
    (`supabase/migrations/0001_init.sql:117-119`) 전체 사용자 이메일이 공개된다
  - `security definer` 함수로 조회 → 마이그레이션 1개. 별명을 넣어보면
    가입 여부를 확인할 수 있는 통로가 새로 생긴다

**C. 전화번호 / OAuth / 익명**
- 전화번호는 SMS 제공자 연동과 과금. OAuth는 결국 이메일을 받는다
- 익명 로그인은 비밀번호가 없어 "로그인" 요구 기능을 못 채운다

## 결정

**A.**

## 이유

Supabase가 비밀번호 로그인에 이메일·전화번호만 받는다.

```
node_modules/@supabase/auth-js/dist/module/lib/types.d.ts:567-573
type PasswordCredentialsBase = { email; password } | { phone; password };
```

B는 요구 기능 6개 중 "로그인" 하나를 위해 마이그레이션과 보안 판단을 얹는다.
이메일은 필드 하나 값으로 로그인 키 · 계정 유일성 · 나중의 비밀번호 재설정 경로를 같이 산다.

별명은 그대로 받되 역할이 다르다 — 이메일은 비공개 식별자, 별명은 글·댓글·팔로우에 붙는
공개 이름이다(`0001_init.sql:59`). 이메일 앞부분으로 별명을 자동 생성하면 이메일이 공개된다.

## 비용

사용자가 가입에 쓴 이메일을 기억해야 한다. 비밀번호 재설정은 아직 구현하지 않았다.
