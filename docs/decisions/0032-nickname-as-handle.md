# 0032. 아이디를 없애고 별명을 유일한 이름으로, 주소는 id로 한다

- 상태: 확정
- 날짜: 2026-09-14
- 대체: [0011](0011-profile-routes.md)의 주소 `/u/[username]`

## 맥락

로그인은 이메일이다(결정 0001). `profiles.username`은 로그인에 쓰이지 않고 주소 `/u/[username]`과 `@username` 표시에만 쓰였다.
가입 폼은 이 칸을 "별명"이라 부르고 트리거가 같은 값을 `display_name`에도 넣어, 헤더에 같은 글자가 두 줄로 보였다.
프로필 편집(결정 0030)으로 `display_name`을 바꿀 수 있게 되자 사람을 부르는 이름이 둘이 됐다.
사용자가 아이디는 관리할 필요가 없는 컬럼이라고 판단했고, 가입 때 받는 별명을 그 자리에 쓰기로 했다.

## 선택지

**주소**

- A. `/u/<id>`(uuid): 별명을 바꿔도 주소가 그대로다. 사람이 읽을 수 없다
- B. 별명을 주소로: 읽을 수 있지만 별명을 바꾸면 주소가 바뀌고 옛 링크가 깨진다. 한글, 공백을 인코딩해야 한다

**별명 겹침**

- A. 허용: 가입이 쉽다. 같은 이름의 두 사람을 화면에서 구별할 길이 사진뿐이다
- B. 금지, 대소문자 무시: 이름이 곧 구별자다

**적용 순서**

- A. 마이그레이션 하나로 컬럼을 지우고 코드를 바꾼다: 배포 전까지 main이 없는 컬럼을 읽어 깨진다
- B. 넓히기(0009) → 코드 배포 → 줄이기(다음 마이그레이션): 파일이 둘이지만 어느 순간에도 배포본이 돈다

## 결정

**주소 A, 겹침 B, 순서 B.** 사용자가 주소와 겹침을 골랐다. 순서는 결정 0031 때 정책을 먼저 적용해 배포본의
좋아요 수가 깨졌던 일을 되풀이하지 않으려고 나눴다.

같이 정한 값:

- **유일성은 `lower(display_name)` 유일 인덱스.** 앞뒤 공백은 서버가 저장 전에 지운다(`lib/utils/display-name.ts`)
- **겹침 판정은 DB가 한다.** 가입은 트리거가 터지면 `isDisplayNameTaken`으로 다시 확인하고, 편집은 23505를 별명 칸 에러로 옮긴다
- **탭 제목은 "프로필", "팔로워", "팔로잉".** 주소에 이름이 없어 제목을 위해 프로필을 한 번 더 읽지 않는다
- **옛 주소를 새 주소로 보내지 않는다.** 공유된 링크가 거의 없는 초기 단계다

## 비용

- 주소를 읽고 누구인지 알 수 없다
- 같은 사람 프로필이라도 탭 제목이 모두 "프로필"이라 스크린리더 사용자가 문서 제목으로 구별하지 못한다
- 줄이기 마이그레이션 전까지 `username` 컬럼이 남아 새 가입자는 null이다
