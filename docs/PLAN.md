# 8around SNS — 3일 실행 계획

## 스택 (확정)

| 영역 | 선택 | 이유 |
|------|------|------|
| 프레임워크 | Next.js (App Router) + TypeScript strict | 서버 컴포넌트로 데이터 페칭 레이어를 따로 안 만듦 |
| DB / 인증 | Supabase (Postgres + Auth + RLS) | 요구 기능 6개 중 회원가입·로그인이 설정으로 끝남 |
| 배포 | Vercel | push = 프리뷰 URL. 1일차에 체험 가능한 URL 확보 |
| 린트/포맷 | Biome | ESLint + Prettier + 플러그인들을 의존성 하나로 대체 |
| 테스트 | Vitest | 심사 시나리오 방어용 최소 테스트만 |

권한 검증은 **RLS 한 곳**에서만 한다. 앱 코드에 소유권 체크를 중복으로 두지 않는다.

---

## Day 1 — 하네스 + 인증 (기반을 먼저 굳힌다)

### AM. 하네스 (기능보다 먼저)
기능을 다 만든 뒤에 하네스를 깔면 린트 에러 수백 개가 한꺼번에 터진다. 빈 레포일 때 깔면 공짜다.

- [ ] `create-next-app --typescript`, `tsconfig.json`에 `"strict": true`
- [ ] Biome 설치 + `biome.json` (lint + format 통합)
- [ ] GitHub Actions 워크플로 **1개**: `biome ci` → `tsc --noEmit` → `vitest run` → `next build`
- [ ] `CLAUDE.md`: 폴더 규칙 / DB 접근 위치 / 커밋·PR 규칙 / "새로 합류한 사람이 읽을 한 페이지"
- [ ] Vercel + Supabase 프로젝트 연결, 환경변수 세팅

**DoD:** 빈 화면이지만 배포 URL이 살아있고, PR 하나에 CI가 초록으로 돈다.

### PM. 스키마 + 인증
- [ ] 마이그레이션 파일로 4테이블 생성 (대시보드 수동 편집 금지 — 재현이 안 된다)
  - `profiles` — id(auth.users FK), username, display_name, bio
  - `posts` — id, author_id, content, created_at
  - `comments` — id, post_id, author_id, **parent_id (self FK, nullable)**, content
  - `follows` — follower_id, following_id (복합 PK)
- [ ] RLS 정책: 읽기는 전체 공개, 쓰기/삭제는 본인만
- [ ] 회원가입 → 프로필 생성 → 로그인 → 세션 유지 관통

**DoD:** 배포된 URL에서 실제로 가입하고 로그인된다.

## Day 2 — 기능 수직 관통 (스타일은 최소로)

한 기능씩 **UI + 쿼리 + 배포**까지 끝내고 다음으로 넘어간다. 화면을 전부 만들고 나중에 API를 붙이는 순서는 금지 — 마지막 날에 통합 지옥이 온다.

### AM. 콘텐츠
- [ ] 게시글 작성 → 피드 노출
- [ ] 댓글 작성
- [ ] 대댓글 (`parent_id`로 1뎁스 트리 렌더)

> 대댓글은 **1뎁스까지만** 편다. 무한 중첩은 요구사항이 아니고 모바일에서 읽히지도 않는다.

### PM. 소셜
- [ ] 팔로우 / 언팔로우 토글
- [ ] 팔로워 · 팔로잉 목록
- [ ] 팔로잉 기준 피드 필터

**DoD:** 요구 기능 6개가 배포본에서 전부 동작한다. 이 시점에 기능은 끝이다.

## Day 3 — 디자인 패스 + 마감 (점수가 갈리는 날)

### AM~PM. 디자인
Day 1~2에서 스타일을 미뤄둔 이유: 기능이 덜 된 상태로 디자인하면 두 번 하게 된다.

"AI가 만든 티"를 피하는 것은 **기본값을 쓰지 않는 것**이다.

- [ ] 타이포 스케일과 스페이싱 스케일을 **먼저** 정하고 토큰화 (색부터 정하면 그라데이션 함정에 빠진다)
- [ ] 확정한 값은 `docs/DESIGN.md`에 기입 — 이 시점이 그 파일을 채우는 때다
- [ ] 카드 테두리 + 그림자 남발 대신, **여백과 구분선**으로 위계를 만든다
- [ ] 색은 무채색 + 강조색 1개. 그라데이션 없음
- [ ] 인터랙션
  - 낙관적 업데이트: 팔로우 / 댓글 작성은 서버 응답 전에 즉시 반영
  - 상태 3종: 로딩(스켈레톤) / 빈 상태(문구+행동 유도) / 에러
  - 포커스 링, 전환은 150~200ms 이내

### 마지막. 애니메이션 (UI + 기능이 다 선 뒤에)
동작하는 화면 위에 얹는다. 레이아웃이 흔들리는 중에 모션을 넣으면 두 번 작업이 된다.

- [ ] 목록 진입 / 댓글 추가 시 fade + 살짝의 y 이동 (12px 이내)
- [ ] 팔로우 토글, 좋아요류 버튼의 눌림 피드백
- [ ] 모달 · 시트 열고 닫힘
- [ ] 전부 CSS transition 우선. 라이브러리는 CSS로 안 될 때만
- [ ] `prefers-reduced-motion` 존중

과하면 "AI 티"로 되돌아간다. 사용자의 행동에 **반응하는** 것만 넣고, 알아서 움직이는 장식은 넣지 않는다.

### PM. 마감
- [ ] 심사 시나리오 E2E 1개: 가입 → 로그인 → 글 작성 → 댓글 → 대댓글 → 팔로우
- [ ] 위 시나리오를 **배포 URL에서 사람 손으로** 한 번 직접 통과
- [ ] README: 배포 URL, 체험 경로, 테스트 계정, 로컬 실행 방법

## 범위 밖 (의도적으로 안 만든다)

알림, DM, 좋아요, 이미지 업로드, 무한 스크롤, 해시태그, 검색 — 요구사항이 아니다.

시간이 남으면 **이미지 업로드**부터 (Supabase Storage로 짧게 끝난다).

## 3일로 압축하며 잘라낸 것

- 디자인 패스 2일 → **1일**. 토큰 정의와 상태 3종을 먼저 끝내고, 애니메이션은 UI·기능이 다 선 뒤 마지막에 얹는다.
- 컴포넌트 단위 테스트 → **E2E 시나리오 1개**. 심사자가 밟는 경로만 방어한다.
- 스키마 설계 회차 분리 → 4테이블을 **한 번에** 확정. 마이그레이션으로 관리하니 수정 비용이 낮다.
